## Where inconsistency can enter a financial workflow

Financial operations often cross several boundaries: an API request, a database transaction, a scheduled calculation, and a later reconciliation. Each boundary creates a place where retries, stale state, or partial failure can affect the result.

Useful design questions include:

- Can the same request be received more than once?
- Which account state permits this operation?
- Which period and product rules apply to a calculation?
- How can recorded movements be compared with the expected account state?

These are general design concerns for credit and payment software. Their answers depend on the product's rules and data model.

---

## Make retryable operations idempotent

Network timeouts do not tell a client whether the server committed a request. A retry can therefore repeat an operation unless the API defines how duplicate requests are recognized.

An idempotent operation produces the same business effect when the same request is submitted again. A design may combine:

- an idempotency key scoped to the business operation;
- a database uniqueness constraint for the relevant business identity;
- a stored result that lets a retry receive the original outcome;
- transaction boundaries that commit the business change and its idempotency record together.

The key must represent the intended operation, not merely the HTTP connection. Expiration, reuse, and conflicting payloads also need explicit rules.

---

## Validate state transitions before applying them

Financial actions are valid only under defined conditions. A payment, charge, reversal, or installment change should check the current account state and the business rules for the transition.

A transition can be modeled as:

1. Load the relevant state within the transaction boundary.
2. Validate the requested action against the allowed transition and its invariants.
3. Apply the state change and related ledger entries atomically where the data model permits.
4. Record enough context to explain the decision later.

This makes invalid transitions explicit and gives concurrent requests a clear point at which to detect stale state.

---

## Treat interest rules as product rules

Interest calculations depend on the agreement, principal, balance history, applicable period, and product-specific rules. These inputs should be explicit rather than inferred from whichever records happen to be available during a calculation.

For repeatable calculations, define the effective date and period boundaries, keep the rule version visible, and make reruns safe. The exact rule belongs to the product contract; a technical pattern should not silently define it.

---

## Reconcile recorded movements with expected state

Preventive controls cannot answer every question after an operation has been processed. Reconciliation compares related records or independently derived balances to find differences that need explanation.

Examples of comparison dimensions include:

- payments and their applications;
- charges and the periods they cover;
- ledger movements and the resulting account balance.

Each comparison needs a documented source of truth, tolerance where rounding is involved, and a way to distinguish a real exception from an incomplete or delayed input.

---

## Make exceptions reviewable

When a comparison finds a difference, preserve the input references, rule version, and calculation context. Classify the exception so an operator can distinguish missing data, a timing difference, a rejected transition, and a potential correction.

Detection and correction are separate decisions. The correction path should be authorized, traceable, and safe to retry; the appropriate degree of automation depends on the financial rules and operational controls.

---

## Keep an audit trail of decisions

An audit record should explain what changed, which business action caused it, and which rule or state transition was applied. It should preserve the link between a request and its resulting financial movements without duplicating sensitive payment data unnecessarily.

Idempotency, state validation, reconciliation, and auditability address different failure modes. Together they make financial workflows easier to reason about while keeping product rules explicit.
