## Reconciliation is part of the system design

Reconciliation compares related records or an independently derived state to find differences that the main transaction path cannot explain on its own.

It is useful to design the comparison alongside the workflow that produces the records. That makes the source of truth, relevant identifiers, and expected state transitions explicit before an exception needs investigation.

---

## Define what the job compares

Start with a specific relationship rather than a broad scan. For example, a reconciliation rule may compare:

- a payment with its allocation to an account;
- a charge with its effective period;
- ledger movements with a derived balance.

Document which system or record owns each value. If data can arrive asynchronously, distinguish a temporarily incomplete input from a true difference.

---

## Make each run repeatable

A reconciliation job may be scheduled or triggered by an event. Its cadence depends on the freshness requirement, data volume, and operational capacity; frequency alone does not demonstrate effectiveness.

For safe retries, give each comparison a stable identity and make output writes idempotent. Process bounded batches, persist progress where needed, and ensure a rerun does not create duplicate exceptions or alter the source financial records.

---

## Classify differences before acting

Not every mismatch has the same cause. A useful result can distinguish:

- missing or delayed input;
- timing differences between related records;
- a rule or state transition that needs investigation;
- a value outside an explicitly defined tolerance.

The classification should retain references to the compared records and the rule version used. This gives reviewers enough context to reproduce the comparison.

---

## Separate detection from correction

The reconciliation process identifies and records a difference. A correction path then follows the authorization and audit rules of the product.

Some exceptions may be resolved automatically when the rule is deterministic and the operation is safe to repeat. Others need an authorized review. In either case, record the decision and preserve the original movements so a later reviewer can understand the change.

---

## Design for operational review

An exception queue is useful only when each item explains what was compared, what differed, and which next action is available. Keep retries, alerting, and resolution status visible without treating an alert as proof that the financial state has been corrected.

These design choices make reconciliation a reviewable control: it checks consistency, preserves evidence, and leaves product-specific correction policy explicit.
