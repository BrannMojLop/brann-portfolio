# Portfolio Experience V3 — Strategy review

Reviewer: `portfolio-strategist`

## Result

`PASS` for visual-positioning direction. No public claim or approved copy was
rewritten.

## Positioning diagnosis

The current content supports Software Architecture / Technical Leadership, but
the visual language still distributes attention like a general developer
portfolio. The strongest differentiator is already present in the content:
business constraints, architecture decisions, explicit responsibility,
evidence, and current state. The UI should make those relationships visible.

## Target experience

The visitor should understand, in order:

1. what kind of engineer this is;
2. which systems demonstrate that practice;
3. how architecture decisions respond to constraints;
4. how current engineering work is organized and reviewed;
5. how to continue into evidence or start a conversation.

This is an information-architecture goal, not a request to add claims or enlarge
the job-title treatment.

## Recommended message hierarchy by surface

- Home: positioning → compact proof → selected systems → engineering process →
  next action.
- Systems: domain/context → responsibility → decision/constraint/state → full
  case evidence.
- About: current role and progression → capabilities → working method → public
  references.
- Engineering: current practice and recent notes → themes → archive.
- Contact: conversation fit → primary contact action → secondary references.

## Differentiation assessment

The site is differentiated in tone and subject matter, but not yet fully in
visual structure. Repeated card surfaces and ambient “systems” motifs make it
feel adjacent to a polished portfolio template. A quieter editorial layout with
decision rows, case-study summaries, and current-note prioritization would make
the same approved content feel more senior and specific.

## Guardrails

- Do not add titles, metrics, production status, client counts, or expertise
  claims.
- Do not turn the site into an AI-themed marketing experience.
- Do not remove technical depth to achieve visual simplicity.
- Do not change the approved EN/ES content architecture without a later content
  decision.
